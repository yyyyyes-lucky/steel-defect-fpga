# AI 协助的工程决策与实践心得

本记录围绕关键工程问题，按“问题—AI 协助—人工判断—验证—结论”总结技术方案的形成与取舍。最终方案、参数取舍、是否继续测试和是否纳入交付，均由项目成员根据实际板测、图像检查和资源报告决定。

## 1. 明确软硬件分工

**工程问题：**完整 YOLO 网络是否放进 FPGA，以及开发板在演示链路中承担什么工作。

**AI 协助：**根据现有 Windows 摄像头程序、板端接口、FPGA 资源和已有运行代码，梳理出可落地的数据流，并区分检测、后处理和显示的计时边界。

**人工判断与采取：**项目成员确定 Windows 运行 YOLO，开发板执行冻结检测框之后的后处理；FPGA 加速 Sobel、局部统计和 Gaussian 等已有硬件路径，板端 PS 软件负责类别分流、候选区域和统计。这个范围适合现有板卡和演示时间，也避免把“检测框来自 YOLO”误写成“YOLO 已在 FPGA 上运行”。

**验证与结论：**静态网页和动态会话均按“电脑检测 → 开发板后处理 → 电脑显示/保存”组织。裂纹最终只展示 YOLO 检测框和置信度，未虚构 FPGA 生成的精确裂纹掩膜。

## 2. 从核速度转向整条后处理路径

**工程问题：**更快的硬件核可能被数据准备、DMA、缓存维护、等待、解包和剩余 PS 工作抵消。

**AI 协助：**帮助拆分阶段耗时，建立“可消除工作 + 新增传输/调度成本 + 剩余软件”的替换预算，并提醒不能把混合的 `launch/DMA/core/wait` 全部称为纯 DMA 时间。

**人工判断与采取：**项目成员主动提出 DMA 开销问题，并要求避免重复工作。后续优先复用已有特征、采用 Q8 staged/minmax 和 explicit cache 路径；对新增融合核采用系统级配对计时，而不是只看 HLS 核报告。

**验证与结论：**F1 平均只节省约 0.619%，8 个会话对的 95% 节省区间跨零，因此未晋级；P2/F3 初筛整体慢约 1.216%，停止该实现；v15、v16 的局部正确性也没有被写成整体加速。结论是：硬件优化必须以系统路径为评价对象。

## 3. 硬件候选的采用与停止

**工程问题：**哪些候选值得继续占用 FPGA 资源，哪些只是功能通过但没有稳定收益。

**AI 协助：**整理 v11～v16、F1 和 P2/F3 的输入范围、计时边界、资源占用和输出一致性，生成候选对照表，并提示不能跨实验叠加百分比。

**人工判断与采取：**项目成员要求先复用已有结果、减少重复测试；根据全量或配对证据决定“采用、停止本实现或证据不足”。最终采用 v10 硬件 + v9.1 软件 + Q8/cache 及选定掩膜算法，不把所有通过功能检查的候选塞进最终工程。

**验证与结论：**v13 class2 融合全量约 1.00566×，资源接近 BRAM 上限，未采用；v15 全量增加约 5.998%，未采用；v16 受影响帧增加约 0.745%，保留 PS 路径。具体范围见 [优化取舍](optimization_history.md) 和 [历史证据](../data/optimization_evidence/readme.md)。

## 4. 按类别审查图像算法

**工程问题：**程序成功运行不代表掩膜视觉效果正确。阈值附近、纹理粘连、区域破碎和面积过滤都可能改变结果含义。

**AI 协助：**提供逐类复核、保存原始输出、单参数对照和连通域统计的流程，并把检测框、候选掩膜、粗分割和统计结果区分开。

**人工判断与采取：**项目成员查看实际图像后要求扩大检查范围，而不是只修一张截图；明确裂纹只保留检测框，划痕保留旧算法，其余类别采用人工复核后认为可接受的调整分支。

**验证与结论：**低阈值下纹理可能连成接近整图的大区域，提高阈值又可能产生大量碎片。因此，候选像素和连通域数量只能作为统计，不能直接当真实缺陷数或分割精度。相关通用流程已整理为 [图像算法与掩膜验证技能](../skill/general/algorithm_validation/readme.md)。

## 5. 用同输入证明加速范围

**工程问题：**如何区分 FPGA 后处理收益、YOLO 推理耗时和摄像头系统端到端延迟。

**AI 协助：**设计相同灰度输入、相同冻结检测框、同一板卡、交替顺序和两轮配对的 ARM/FPGA 比较，并保留慢帧、未检出帧和输出差异。

**人工判断与采取：**项目成员要求使用数据集做静态演示，并要求页面同时展示原图、ARM、FPGA 和加速对比；接受“板端后处理加速”这一准确口径，不把它扩大成摄像头端到端加速。

**验证与结论：**最近两组硬件各使用 120 张 valid 图片、317 个 ROI、两轮共 480 次测量：参考硬件约 3.354×，重构建硬件约 3.329×。两组结果和网页见 [复刻证据](../data/reproduction_20261031/index.html)。这证明的是指定输入和计时边界下的板端后处理收益，不是完整 YOLO 或长期实时性能证明。

## 6. 把实际踩坑提炼成工程规则

**工程问题：**复刻时出现旧 HLS 命令、Notebook 自校验、工作目录混淆和网页导出缺少展示元数据等问题。

**AI 协助：**根据第一处真实报错定位执行位置、工具版本、文件布局和数据契约，并把修复后的最小回归加入工程检查。

**人工判断与采取：**项目成员通过实际复刻和运行发现问题，要求取消会因 Notebook 执行而失效的文件哈希通行门槛，同时保留真正的接口、超时和硬件状态检查；之后又检查网页是否能显示真实图片，而不是只看 HTML 文件存在。

**验证与结论：**构建入口按 Vivado/Vitis 2026.1 记录；Notebook 运行不再因自身输出变化而被拒绝；静态网页补回图片名称和类别后，筛选、局部放大、图层切换和换目录离线打开均通过。这个过程沉淀为 [复现问题定位技能](../skill/general/reproduction_troubleshooting/readme.md)，但本项目的命令和路径不应直接复制到其他工程。

## 7. AI 协助与人工工作的边界

### 人工完成的关键工作

- 提出项目目标、演示约束和“不能重复浪费测试”的要求；
- 发现 DMA 开销、掩膜效果和网页对应关系等实际问题；
- 决定软硬件分工、裂纹输出形式、划痕旧分支和候选停止条件；
- 上传/运行板端程序、查看真实图像、完成静态和动态板测并保存结果；
- 根据结果决定最终采用什么，以及交付包保留哪些证据。

### AI 提供的协助

- 分析代码、接口、日志和结果 JSON；
- 起草候选预算、比较脚本、网页和复现步骤；
- 帮助定位报错、整理实验边界和生成可复用模板；
- 对人工提出的方案进行数据汇总、差异检查和回归验证。

AI 输出必须经过代码运行、图像检查、板端测量或文件核对后才能进入结论。没有实测证据的内容保留为假设或待验证事项，不写成已经完成。
